# Containerização e execução local com Docker

O projeto foi organizado em três serviços independentes no Docker Compose:

- `frontend`: aplicação SvelteKit executada com Node.js;
- `backend`: API Flask executada com Gunicorn;
- `database`: banco PostgreSQL 17.

Essa separação permite construir, testar e futuramente publicar frontend e
backend como imagens independentes. O treinamento e a inferência de machine
learning não fazem parte desses containers transacionais; a evolução planejada
está descrita em
[`docs/architecture/containerizacao-e-ml.md`](../architecture/containerizacao-e-ml.md).

## Arquivos Docker do projeto

- `compose.yaml`: declara os três serviços, portas, variáveis, redes, volume,
  dependências e healthchecks;
- `docker/frontend/Dockerfile`: constrói o frontend e cria uma imagem de runtime
  contendo somente o build de produção;
- `docker/backend/Dockerfile`: instala as dependências Python, copia a API e
  configura o Gunicorn;
- `.dockerignore`: exclui do contexto de build arquivos desnecessários ou
  sensíveis, como `.env`, `node_modules`, `.git` e caches;
- `.env.example`: modelo versionado das variáveis necessárias;
- `.env`: configuração local real, não versionada e não copiada para as imagens;
- `src/lib/server/schema.sql`: schema montado no container PostgreSQL durante a
  primeira criação do volume de dados.

## Diferença entre imagem e container

Uma imagem é um artefato imutável criado a partir de um Dockerfile. Ela contém o
runtime, as dependências e o código necessários para iniciar um serviço. Um
container é uma instância em execução dessa imagem, com rede, variáveis de
ambiente e uma camada gravável temporária próprias.

O Compose constrói duas imagens locais:

- `fabritag-frontend:latest`, baseada em `node:22-alpine`;
- `fabritag-backend:latest`, baseada em `python:3.12-slim`.

O banco utiliza diretamente a imagem oficial `postgres:17-alpine`, obtida do
Docker Hub. A imagem do frontend usa um build em múltiplos estágios: o primeiro
instala as dependências e executa `pnpm run build`; o segundo recebe somente o
diretório `build` e inicia a aplicação com Node.js. A imagem do backend instala
`requirements.txt`, copia `src/lib/server` e inicia a API com Gunicorn.

As imagens não são criadas como arquivos dentro do repositório. No Windows com
Docker Desktop, elas e suas camadas são armazenadas no disco Linux interno
gerenciado pelo Docker Desktop/WSL. Esse armazenamento deve ser administrado
pelos comandos e pela interface do Docker, sem editar os arquivos internos do
WSL manualmente.

Comandos úteis para consultar os artefatos locais:

```powershell
docker compose images
docker image ls
docker compose ps
docker volume ls
```

Em uma futura implantação em nuvem, as imagens de frontend e backend deverão ser
publicadas em um registry de containers. O ambiente de execução fará o pull das
imagens desse registry; credenciais e demais configurações continuarão sendo
fornecidas em tempo de execução, por variáveis ou por um secret manager.

## Redes, portas e persistência

O Compose cria duas redes:

- `edge`: conecta frontend e backend;
- `data`: conecta backend e PostgreSQL e é marcada como interna.

Dentro dessas redes, os serviços usam seus nomes DNS. O frontend acessa
`http://backend:5000`, e o backend acessa o host `database` na porta `5432`.
Esses endereços internos são diferentes das portas publicadas no Windows:

- frontend: `http://localhost:3000` por padrão;
- backend: `http://localhost:5000` por padrão;
- PostgreSQL: `127.0.0.1:5432` por padrão.

As portas externas podem ser alteradas no `.env`. Neste computador, por
exemplo, `POSTGRES_HOST_PORT=5433` evita conflito com um PostgreSQL local que já
utiliza a porta `5432`. Essa alteração não muda a comunicação interna entre o
backend e o banco.

Os dados do PostgreSQL ficam no volume nomeado `fabritag_postgres_data`. Por
isso, remover e recriar o container não apaga o banco. O `schema.sql` é executado
automaticamente somente quando esse volume é criado pela primeira vez.

## Variáveis de ambiente

O `.env` deve permanecer na raiz, ao lado de `compose.yaml`. O Compose lê esse
arquivo para preencher portas, credenciais e endereços, e repassa a cada serviço
somente as variáveis declaradas em `compose.yaml`.

O `.dockerignore` exclui `.env` e arquivos equivalentes do contexto de build.
Consequentemente, senhas locais não são gravadas nas imagens. Antes de iniciar,
é necessário definir senhas próprias em `DB_PASSWORD` e `ADMIN_PASSWORD`; a
senha administrativa deve ter pelo menos seis caracteres.

## Como construir e inicializar

Pré-requisitos:

- Docker Desktop iniciado com o backend WSL 2;
- arquivo `.env` criado na raiz do projeto;
- portas configuradas no `.env` disponíveis no Windows.

Na raiz do repositório, crie o arquivo local na primeira execução:

```powershell
Copy-Item .env.example .env
```

Edite o `.env`, valide a configuração e construa as imagens:

```powershell
docker compose config --quiet
docker compose build
```

Inicie os serviços em segundo plano e aguarde os healthchecks:

```powershell
docker compose up -d --wait --wait-timeout 180
```

Também é possível construir e iniciar em uma única operação:

```powershell
docker compose up --build
```

O fluxo de inicialização é sequencial: o PostgreSQL precisa ficar saudável para
o backend iniciar, e o backend precisa responder em `/api/status` para o
frontend iniciar. O estado pode ser acompanhado com:

```powershell
docker compose ps
docker compose logs -f
```

Após a inicialização:

- aplicação: `http://localhost:3000`;
- status da API: `http://localhost:5000/api/status`;
- dispositivos RFID: API publicada na porta configurada em `BACKEND_PORT`;
- banco para ferramentas locais: `127.0.0.1` na porta definida por
  `POSTGRES_HOST_PORT`.

## Como parar ou recriar

Para encerrar os containers e preservar o banco:

```powershell
docker compose down
```

Depois de alterar código ou dependências, reconstrua e suba novamente:

```powershell
docker compose up -d --build --wait
```

O comando abaixo também remove o volume e apaga permanentemente os dados do
PostgreSQL do ambiente Docker. Ele deve ser usado somente quando a intenção for
reinicializar completamente o banco:

```powershell
docker compose down --volumes
```

## Validação realizada

As imagens de frontend e backend foram construídas no Docker Desktop e os três
containers passaram nos healthchecks. Também foram verificados:

- frontend respondendo HTTP 200 em `/login`;
- backend respondendo HTTP 200 em `/api/status`;
- PostgreSQL aceitando conexões;
- ausência de erros recentes nos logs dos serviços.
