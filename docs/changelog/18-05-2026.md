## 1. Leituras RFID registrando entrada como saída

### Problema

A tag `4ED11707` entrava e saía da câmara corretamente, mas a tag `79D24D05` registrava apenas saídas. Na prática, toda nova leitura dessa tag acabava virando uma movimentação de saída.

### Como era antes

No backend, eventos `REMOVED` eram ignorados de propósito, e cada evento `ARRIVED` funcionava como um alternador de estado:

- se o lote estava fora da câmara, `ARRIVED` virava `Entrada`;
- se o lote já estava na mesma câmara, `ARRIVED` virava `Saída`.

Esse modelo depende de o firmware enviar apenas um `ARRIVED` por passagem física da tag.

No firmware, uma tag era considerada removida após apenas 3 leituras falhas seguidas. Como o loop roda a cada ~50 ms, uma pequena perda de leitura por cerca de 150 ms já podia marcar a tag como removida.

### Causa provável

A tag `79D24D05` provavelmente tinha leitura mais instável, distância pior, orientação ruim ou resposta NFC/RFID mais fraca. Com isso, o PN5180 podia perder a tag por alguns ciclos e depois reencontrá-la. O firmware então enviava outro `ARRIVED`, e o backend alternava o estado para `Saída`.

### O que mudou

Arquivos alterados:

- `firmware/firmware.ino`
- `src/lib/server/database_manager.py`

Mudanças:

- `tagRemovedMissLimit` aumentou de `3` para `20`.
- Foi criado um debounce no backend de 5 segundos para ignorar chegadas duplicadas da mesma tag no mesmo sensor.

### O que isso corrige

Agora pequenas falhas temporárias de leitura não geram uma nova chegada falsa. Mesmo que o firmware envie uma chegada duplicada em poucos segundos, o backend ignora e não alterna a movimentação para saída.

## 2. Limpeza do banco de dados de testes

### Problema

O banco PostgreSQL tinha apenas movimentações de teste, mas os dados de login deveriam ser preservados.

### Orientação dada

Foi sugerido limpar somente os registros operacionais, mantendo `USUARIO` e os `CLIENTE` ainda referenciados por usuários.

SQL completo sugerido:

```sql
BEGIN;

TRUNCATE TABLE
  LEITURA_BRUTA,
  LOTE_PRODUTO_ASSOC,
  LOTE_TAGGEADO,
  SENSOR,
  DISPOSITIVO,
  CAMARA,
  PREDIO,
  PRODUTO_TIPO
RESTART IDENTITY CASCADE;

DELETE FROM CLIENTE c
WHERE NOT EXISTS (
  SELECT 1
  FROM USUARIO u
  WHERE u.cliente_id = c.id
);

COMMIT;
```

Também foi sugerida uma limpeza menor, preservando infraestrutura:

```sql
BEGIN;

TRUNCATE TABLE
  LEITURA_BRUTA,
  LOTE_PRODUTO_ASSOC,
  LOTE_TAGGEADO
RESTART IDENTITY CASCADE;

COMMIT;
```

### O que isso resolve

Remove movimentações, lotes e leituras de teste sem apagar usuários, senhas e login.

## 3. Dashboard não atualizava movimentações em tempo real

### Problema

Após uma nova movimentação, era necessário atualizar manualmente a página para ver a nova linha na tabela de últimas movimentações.

### Como era antes

A página `/dashboard` carregava os dados uma vez via `+page.server.js`, buscando `/api/dashboard` no backend Flask. Depois do carregamento inicial, não havia polling, WebSocket, Server-Sent Events ou invalidação automática da rota.

### O que mudou

Arquivo alterado:

- `src/routes/dashboard/+page.svelte`

Mudanças:

- O dashboard agora mantém os dados em estado local reativo.
- A página chama `http://127.0.0.1:5000/api/dashboard` a cada 2 segundos.
- As movimentações recebidas são enriquecidas no cliente com:
  - `date_timestamp`, para filtros de data;
  - `search_index`, para busca textual.
- Foi adicionado um texto de última atualização: `Atualizado HH:mm:ss`.
- Os filtros e a busca atual não são perdidos durante a atualização.

### O que isso corrige

Novas entradas e saídas aparecem automaticamente na tabela sem recarregar a página.

## 4. Navegação bugada pelo sidebar

### Problema

Ao clicar em páginas pelo sidebar, a URL mudava, mas a página às vezes não renderizava. Em alguns casos renderizava uma vez, mas falhava ao clicar rapidamente em outra página.

### Como era antes

O `sensorStore.startPolling()` em `src/lib/dispositivos.svelte.js` era uma função `async`. Isso fazia com que os componentes recebessem uma `Promise` em vez de uma função de limpeza.

Na desmontagem de páginas, o código tentava tratar essa `Promise` como função de cleanup. Isso podia quebrar o ciclo de vida do componente durante a navegação.

Também havia uma página retornando a função errada no cleanup:

```js
return () => stopPolling;
```

Isso retorna a referência, mas não chama `stopPolling()`.

### O que mudou

Arquivos alterados:

- `src/lib/dispositivos.svelte.js`
- `src/routes/infraestrutura/+page.svelte`
- `src/routes/dashboard/+page.svelte`

Mudanças:

- `startPolling()` deixou de ser `async`.
- Agora `startPolling()` retorna imediatamente uma função real de cleanup.
- Se o polling já estiver ativo, retorna uma função vazia segura.
- A página de infraestrutura agora chama corretamente:

```js
return () => stopPolling();
```

- O dashboard também limpa corretamente o polling do sensor e o intervalo de atualização do dashboard.

### O que isso corrige

A navegação do SvelteKit volta a desmontar e montar páginas corretamente. Isso evita o caso em que a URL muda, mas a tela continua presa na página anterior ou fica sem renderizar.

## 5. ESP32 parava após algum tempo ocioso

### Problema

O ESP32 continuava ligado, com LED vermelho aceso, mas depois de algum tempo sem uso parava de ler tags e também parava de enviar ping para o servidor. Era necessário reiniciar manualmente.

### Como era antes

O firmware tinha alguns pontos frágeis:

- `isWifiConnected` era definido como `true` uma vez e nunca revalidado.
- Se o WiFi caísse, o firmware não tentava reconectar de forma controlada.
- O WiFi podia entrar em modo sleep.
- O heartbeat era feito diretamente dentro do `loop()`, sem logging de falha.
- Durante ociosidade, o firmware chamava `recoverNfcRf()` a cada 25 leituras vazias. Com `delay(50)`, isso significava resetar/reconfigurar o PN5180 aproximadamente a cada 1,25 segundo.
- Se alguma chamada do PN5180, SPI, WiFi ou HTTP travasse, não havia watchdog para reiniciar o ESP32.

### Causa provável

Como tanto as leituras quanto o ping paravam, o problema provavelmente era travamento do loop principal. As causas mais prováveis eram:

- recuperação do PN5180 agressiva demais em idle;
- instabilidade em chamada SPI/NFC;
- queda ou sleep do WiFi sem reconexão;
- algum bloqueio interno em HTTP/WiFi/NFC;
- possível instabilidade elétrica no PN5180 ou ESP32.

### O que mudou

Arquivos alterados:

- `firmware/firmware.ino`
- `firmware/network.ino`

Mudanças no firmware:

- Adicionado watchdog do ESP32 com timeout de 15 segundos.
- O watchdog só é iniciado depois do WiFiManager e do health check, para não reiniciar o dispositivo durante o portal de configuração.
- O loop agora chama `esp_task_wdt_reset()`.
- `nfcRecoveryMissLimit` aumentou de `25` para `600`, reduzindo a recuperação NFC em idle de ~1,25 segundo para ~30 segundos.
- Adicionado `handleWiFiConnection()`.
- O firmware agora verifica `WiFi.status()` continuamente.
- Adicionado `WiFi.setSleep(false)`.
- Adicionado `WiFi.setAutoReconnect(true)`.
- Adicionado `WiFi.persistent(false)`.
- Heartbeat foi movido para `sendHeartbeat()`.
- Heartbeat agora registra falhas no Serial Monitor.
- HTTP agora usa `setReuse(false)` para evitar reaproveitamento problemático de conexão.
- `sendTagEvent()` agora só envia se `WiFi.status() == WL_CONNECTED`.

### O que isso corrige

O ESP32 fica mais resistente em idle:

- se o WiFi cair, ele tenta reconectar;
- se o WiFi dormir, isso é evitado;
- se o PN5180 ficar sem tag por muito tempo, ele não é resetado agressivamente a cada segundo;
- se o loop travar, o watchdog reinicia o ESP32 automaticamente em vez de deixar o dispositivo morto até reset manual.
